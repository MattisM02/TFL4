\subsection{Was ist das hier überhaupt?}
\label{sec:was-ist-das}

\textbf{Forschungsfrage:} Welche JVM-Konfiguration minimiert Startup-Zeit,
Latenz und Speicherverbrauch einer Spring-Boot-Anwendung unter harten
Container-Constraints (1\,CPU, 768\,MB RAM)?

Dieses Projekt ist das \textbf{Mess-Werkzeug} für eine wissenschaftliche
Arbeit zum Thema „Ressourcenoptimierung von javabasierten
Containeranwendungen im Cloudbetrieb". Es vergleicht \textbf{32
	Konfigurationen} (20 Flag-Varianten + 12 Laufzeitprofile) automatisiert
und reproduzierbar.

Das Framework besteht aus zwei Teilen:

\begin{enumerate}
	\item
	      \textbf{Die Anwendung unter Test} -- eine Spring-Boot-REST-API, die
	      synthetische Workloads bereitstellt (JSON-Serialisierung,
	      Speicherallokation) sowie einen realen Workload (EBICS-Banktransfer
	      über einen echten Bankserver).
	\item
	      \textbf{Der Benchmark-Runner} -- ein Java-CLI-Programm, das
	      automatisch Docker-Container startet, JVM-Flags injiziert, Metriken
	      erfasst und die Ergebnisse als CSV, JSON und Excel exportiert.
\end{enumerate}

\subsection{Wie läuft ein Benchmark-Durchlauf ab?}
\label{sec:ablauf}

Pro Konfiguration läuft \textbf{genau ein Container gleichzeitig} (keine
parallelen Runs, keine Interferenzen). Jede Konfiguration wird
\textbf{3-mal wiederholt}; der Gesamtdurchlauf dauert \textbf{ca.\ 8–12
	Stunden}.

\begin{enumerate}
	\item \texttt{docker run -{}-cpus 1 -{}-memory 768m} mit injizierten JVM-Flags via \texttt{JAVA\_TOOL\_OPTIONS}
	\item Readiness-Polling alle 150\,ms (max.\ 120\,s) auf \texttt{/actuator/health}
	\item 3 Idle-Snapshots via \texttt{docker stats} (Baseline ohne Last)
	\item First-Request messen (erster echter Aufruf nach Readiness)
	\item 200 Warmup-Requests (verworfen -- JIT soll Steady-State erreichen)
	\item 500 Mess-Requests sequenziell (1 Thread), parallel 10 \texttt{docker stats}-Snapshots
	\item 3 Post-Snapshots (Erholungsverhalten nach Last)
	\item GC-Log aus Container-Stdout extrahieren und parsen
	\item \texttt{docker stop \&\& docker rm}
	\item Ergebnisse als CSV / JSON / Excel exportieren
\end{enumerate}

Der EBICS-Workload läuft gegen einen echten TravicLink-Bankserver
(Docker Compose: PostgreSQL 16 + Applikationsserver), der lokal läuft.
