\section{Kontext-Dokument: JVM-Benchmark-Framework}
\label{sec:kontext}

Dieses Dokument erklärt, was in diesem Projekt technisch passiert -- als
Vorbereitung für ein Experteninterview. Ziel des Interviews: Deine
Praxiserfahrung mit Container-Sizing, Java-Base-Images und relevanten
Ressourcenmetriken aus DevOps-Sicht einzubeziehen.

\medskip\noindent\rule{\linewidth}{0.4pt}\medskip

\subsection{Was ist das hier überhaupt?}
\label{sec:was-ist-das}

Dieses Projekt misst, wie sich verschiedene \textbf{JVM-Konfigurationen}
auf den Ressourcenverbrauch und die Performance einer
Spring-Boot-Anwendung in Docker-Containern auswirken. Es ist kein
Produktionsprojekt -- es ist das \textbf{Mess-Werkzeug} für eine
wissenschaftliche Arbeit zum Thema „Ressourcenoptimierung von
javabasierten Containeranwendungen im Cloudbetrieb".

Das Framework besteht aus zwei Teilen:

\begin{enumerate}
	\item
	      \textbf{Die Anwendung unter Test} -- eine Spring-Boot-REST-API, die
	      synthetische Workloads bereitstellt (JSON-Serialisierung,
	      Speicherallokation) sowie einen realen Workload (EBICS-Banktransfer
	      über einen echten Bankserver).
	\item
	      \textbf{Der Benchmark-Runner} -- ein Java-CLI-Programm, das
	      automatisch Docker-Container startet, JVM-Flags injiziert, Metriken
	      erfasst und die Ergebnisse als CSV, JSON und Excel exportiert.
\end{enumerate}

\medskip\noindent\rule{\linewidth}{0.4pt}\medskip

\subsection{Was passiert bei einem Benchmark-Lauf konkret?}
\label{sec:benchmark-ablauf}

Für jede der \textbf{32 Konfigurationen} (unterschiedliche JVM-Flags
oder JVM-Implementierungen) wird folgender Ablauf automatisiert
ausgeführt:

\begin{verbatim}
1.  docker run -d --cpus 1 --memory 768m --memory-swap 768m \
        -e JAVA_TOOL_OPTIONS="<gc-logging> <jvm-flags>" \
        tfl4-ek-bench:<image-tag>

2.  Readiness-Polling (alle 150ms, max. 120s)
       -> /actuator/health/readiness
       -> /actuator/health           (Fallback)
       -> Workload-Endpoint          (letzter Fallback)

3.  docker stats: 3 Idle-Snapshots (Baseline-Ressourcenverbrauch ohne Last)

4.  First-Request messen (erster echter Aufruf nach Readiness)

5.  Warmup: 200 Requests (werden verworfen, JIT soll Steady-State erreichen)

6.  docker stats: 10 Snapshots parallel zur Messphase

7.  Messphase: 500 Requests (sequenziell, 1 Thread)

8.  docker stats: 3 Post-Snapshots (Erholungsverhalten)

9.  GC-Log aus Container-Stdout extrahieren und parsen

10. docker stop && docker rm
\end{verbatim}

Pro Konfiguration läuft \textbf{genau ein Container gleichzeitig} --
keine parallelen Runs, um Interferenzen zu vermeiden. Der
Gesamtdurchlauf mit 3 Wiederholungen dauert ca. 8--12 Stunden.
